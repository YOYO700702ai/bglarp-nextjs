# BGLARP 劇本後台與雙備份架構

## 目標

- AI 暫時不可用時，員工仍能用簡單表單建立、修改、預覽與發布劇本。
- 一次發布同時保留 Supabase 正式版本與 Notion 鏡像，不需要重複輸入。
- 任一外部服務短暫失效時，不把空資料或半完成資料發布到官網。
- 不因同步、圖片或快取策略再次耗盡 Vercel Hobby 額度。

## 資料責任

| 元件 | 責任 |
| --- | --- |
| Supabase | 劇本穩定 ID、草稿、正式版本、員工權限、封面、稽核與同步工作 |
| Notion | 保留既有工作方式與可閱讀鏡像；不是公開網站的即時依賴 |
| Vercel／Next.js | 員工後台、受控 API、正式網站與精準快取更新 |
| AI 機器人 | 使用與員工相同的 API；使用獨立權杖與 idempotency key |

## 發布流程

1. 員工或 AI 儲存草稿，建立不可覆寫的版本紀錄。
2. 發布端點驗證必要欄位與發布權限。
3. Supabase 原子切換 `published_version_id`，舊正式版在成功前持續可用。
4. 建立 Notion 同步工作；成功標示「已同步」，失敗標示「待重試」。
5. 只清除首頁、公開劇本 API 與該劇本詳細頁的快取。
6. 後台讀回正式版本並顯示發布與同步結果。

Notion 暫時失效時，Supabase 正式發布仍可成功，Notion 工作留在 outbox 供手動或低頻重試。這避免一個外部 API 讓員工整筆資料遺失。

## Vercel 用量護欄

- 封面由瀏覽器用 signed upload 直接傳到 Supabase Storage，不經 Vercel Function 轉送。
- 不使用每分鐘全量同步；同步只由建立、修改、發布或人工重試觸發。
- 不因單一本劇本重新部署；使用 `revalidatePath` 精準更新。
- 不讓封面重新進入 Vercel Image Optimization；前台維持原圖／預先壓縮圖策略。
- 初次 Notion 匯入使用一次性管理工具，不由公開請求觸發。

## 權限

| 角色 | 權限 |
| --- | --- |
| editor | 建立、修改草稿、上傳封面、預覽 |
| publisher | editor 權限，加上發布、下架與重試同步 |
| admin | publisher 權限，加上員工與系統管理 |
| ai | 透過獨立伺服器權杖建立或更新草稿；預設不可發布 |

所有寫入都由伺服器再次驗權。瀏覽器不會取得 Supabase service-role key 或 Notion token。

## 分階段啟用

1. **程式與資料表**：建立 migration、後台、API、版本與 outbox，不切換正式前台。
2. **測試環境**：匯入少量 Notion 劇本，測試人工作業、AI 重送、圖片與同步故障。
3. **平行運作**：完整匯入；Supabase 與 Notion 比對一致，前台仍讀既有來源。
4. **切換讀取**：設定前台讀 Supabase 正式 view，Notion 保留鏡像與緊急人工查閱。
5. **觀察與回復**：至少觀察一個 Vercel 計費週期；必要時可立即切回最後成功快照。

## 上線前驗收

- editor 無法發布；publisher 可發布與下架；一般玩家無法進入後台。
- 同一個 `Idempotency-Key` 重送不會建立兩本劇本或兩個版本。
- Notion 失效時，後台清楚顯示待同步且正式網站仍有上一個成功版本。
- Supabase 寫入失敗時不清快取、不顯示發布成功。
- 封面直傳 Supabase，卡片 4:3 與詳細頁完整預覽皆正確。
- 發布單一本劇本不觸發全站部署或全量 ISR 重建。
